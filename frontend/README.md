# Gestor de Inadimplência — Frontend

Painel web da **Via Permuta** para controle de cobrança. Next.js (App Router) + Tailwind CSS v4, hospedado no Vercel, consumindo a API backend (Node/Express) via `NEXT_PUBLIC_API_URL`.

## Stack

- Next.js 16 (App Router, React 19)
- Tailwind CSS v4
- [Tiptap](https://tiptap.dev/) (`@tiptap/react` + `@tiptap/starter-kit` + `@tiptap/extension-text-align` + `@tiptap/extension-text-style`) — editor de texto rico usado na tela `/contratos`
- Tema visual **Sinal** (skill frontend-design) — ver seção própria abaixo
- Autenticação via JWT armazenado em `localStorage`

## Direção visual — tema "Sinal"

Painel interno de uso diário da equipe de cobrança (não é voltado a cliente final), pensado para uma tarefa específica: escanear rapidamente uma tabela densa de associados e identificar quem precisa de atenção. A direção visual segue esse objetivo.

**Paleta** — fundo quase preto (não roxo), com uma única cor de marca elétrica e saturada aplicada de forma consistente em botões primários, estados ativos, foco e ícones:

| Token | Hex | Uso |
|---|---|---|
| `--background` (Tinta) | `#0A0A0D` | Fundo da aplicação |
| `--surface` (Carvão) | `#131318` | Cards, painéis, tabela |
| `--surface-elevated` | `#1E2029` | Inputs, modais, hover |
| `--primary` (Sinal) | `#3D5AFE` | Cor de marca — botões primários, estados ativos, foco, ícones |
| `--accent` (Sinal Claro) | `#7C8BFF` | Variação clara do sinal — eyebrows, detalhes |
| `--foreground` (Osso) | `#F2F3F7` | Texto principal |

As quatro cores de status de atraso (`--status-green` `#22C55E`, `--status-yellow` `#F5B301`, `--status-orange` `#FB7A24`, `--status-red` `#F2454B`) ficam **fora** dessa paleta de marca — são um código de cor semântico fixo, reservado exclusivamente para a faixa de atraso de cada associado, e nunca usado como cor de botão/ícone genérico. Essa separação é deliberada: evita que a cor da marca seja confundida com um indicador de risco.

**Tipografia** — três famílias, cada uma com um papel bem definido:
- **Space Grotesk** (`font-display`) — títulos e os números grandes de destaque (cards de resumo, contador de bloqueios). Usada com moderação.
- **IBM Plex Sans** (`font-sans`, padrão do corpo) — rótulos, textos, navegação, formulários.
- **IBM Plex Mono** (`font-mono`) — todo dado codificado/numérico: CPF/CNPJ, telefone, valores monetários, datas e timestamps, chave de API. É a decisão tipográfica central do redesenho: numa tabela densa de dados financeiros, o alinhamento tabular do monoespaçado ajuda a equipe a escanear e comparar números/códigos muito mais rápido do que uma fonte proporcional — e distingue visualmente "dado" de "texto corrido" (nome, rótulos) sem precisar de nenhuma cor ou ícone extra.

**Sistema de severidade na tabela** — a intensidade visual de cada linha cresce com a gravidade do atraso: "Em dia" fica neutro (não precisa de atenção), e as faixas Atenção/Alerta/Crítico ganham uma barra de destaque na borda esquerda e um leve tingimento de fundo cada vez mais forte — o vermelho (Crítico) é a linha mais "pesada" visualmente da tabela. Esse é o elemento-assinatura do redesenho: em vez de um badge decorativo, a própria hierarquia de urgência (o motivo de existir dessa tela) é o que dá a personalidade visual à interface.

**Ícones** — conjunto próprio em `components/icons.js` (SVG inline, sem dependência externa), todos com o mesmo traço. Usados dentro de chips circulares preenchidos com a cor de marca (cards de resumo, cabeçalho, chave de API, log de sincronizações) — nunca com as cores semânticas de atraso, para não diluir esse código de cor.

**Cantos e espaçamento** — escala de raio generosa e consistente: `rounded-xl` (12px) em botões/inputs/badges, `rounded-2xl` (16px) em cards/painéis/tabela, `rounded-3xl` (24px) em modais. Espaçamento interno dos cards e da tabela ampliado em relação à versão anterior para dar mais respiração.

## Variáveis de ambiente

Crie um `.env.local` a partir do `.env.example`:

```bash
cp .env.example .env.local
```

| Variável | Descrição |
|---|---|
| `NEXT_PUBLIC_API_URL` | URL base da API backend (ex.: `https://api.viapermuta.com`, sem `/` no final). Exposta ao client pois as chamadas são feitas no navegador. |

## Rodando localmente

```bash
npm install
npm run dev
```

Acesse `http://localhost:3000`. Você será redirecionado para `/login`; após autenticar, o token é salvo no `localStorage` e as rotas de `/dashboard` ficam liberadas.

Build de produção local:

```bash
npm run build
npm run start
```

## Telas

- **`/login`** — usuário/senha (`POST /api/login`), salva o JWT retornado.
- **`/dashboard`** — protegida (redireciona para `/login` se não houver token válido). A partir da versão com paginação do backend, a tabela busca **uma página por vez** em `GET /api/associados` (`page`, `limit=100`), combinando filtro/busca/página numa única chamada:
  - **Cards de resumo** (topo): associados com cobrança em aberto, valor total em aberto, em negociação, bloqueados e no jurídico — sempre refletem a **carteira inteira** (não só a página/filtro ativos na tabela). Vêm de uma **única chamada** a `GET /api/associados/resumo` (números já agregados no banco pelo backend) — não busca mais os associados um por um nem pagina por baixo dos panos para montar esses números, o que reduz bastante as chamadas feitas ao carregar o dashboard (antes crescia com o tamanho da carteira; agora é sempre 1 chamada, independente de ter 50 ou 5.000 associados).
  - **Atalhos de filtro**: Todos, Em Negociação, Bloqueados, Jurídico — enviados como query params (`em_negociacao`/`bloqueado`/`em_juridico`) para o backend, não filtrados no cliente.
  - **Busca**: um único campo de texto (nome, CPF/CNPJ **ou telefone**) enviado como `?busca=` — a pesquisa por telefone acontece no backend, não no cliente. Tem debounce de ~350ms para não disparar uma chamada a cada tecla digitada.
  - **Paginação**: trocar de filtro ou digitar uma busca nova sempre volta a tabela para a página 1. Controles de "Anterior"/"Próxima", indicador "Página X de Y" e total de registros ficam abaixo da tabela (`components/PaginacaoControles.js`).
  - **Ordenação pelo atraso mais crítico primeiro**: o backend agora ordena pelo `dias_diferenca` mais crítico **antes** de paginar (ver README do backend), então a página 1 sempre traz o associado mais crítico do sistema inteiro, e a ordem se mantém correta navegando entre páginas. O frontend **não reordena mais nada no cliente** — a tabela renderiza `associados` exatamente na ordem que a API devolve; a antiga ordenação client-side (`sortByAtrasoDesc`, que só conseguia ordenar dentro da página já carregada) foi removida.
  - **Indicador "sem contato recente"**: um ponto amarelo sutil ao lado do nome (tooltip "Sem contato há Xd") para associados **em negociação** cuja `observacao_atualizada_em` seja nula ou tenha mais de 5 dias — ver `lib/contato.js`. Não aparece para quem não está em negociação.
  - Toggles direto na linha para "Em negociação" (`PATCH .../negociacao`), "Bloqueado" (`PATCH .../bloqueio`) e "Jurídico" (`PATCH .../juridico`) — atualização otimista local: tanto a linha da tabela quanto o contador correspondente nos cards de resumo (+1/-1) são ajustados na hora, sem esperar resposta do servidor nem refazer a chamada de resumo inteira; em caso de erro, os dois voltam ao valor anterior. Como consequência, se um associado deixar de bater com o filtro ativo (ex.: desmarcar "Em negociação" enquanto o atalho "Em Negociação" está selecionado), ele só some da lista na próxima navegação de página/filtro/busca, não instantaneamente.
  - **AJUSTE 10 — toggle "Jurídico" cria/exclui card automaticamente**: marcar liga o associado a um card no Kanban Jurídico (criado sozinho na primeira etapa do quadro, se ele ainda não tiver um em aberto) e desmarcar exclui de vez o(s) card(s) vinculados — tudo do lado do backend, na mesma chamada `PATCH .../juridico` (ver README do backend, seção "AJUSTE 10"). A resposta traz um campo `juridico` que o Dashboard usa pra decidir se mostra um aviso (ver bullet do aviso, logo abaixo da tabela na seção "Layout" — banner laranja com um link "Ver no Jurídico"): aparece só quando o associado **já** tinha um card aberto (nenhum card novo foi criado) ou quando a franquia ainda não tem nenhuma etapa cadastrada; criação e exclusão automáticas "silenciosas" (o caminho normal) não mostram nada — o próprio toggle já é a confirmação visual.
  - **Botão "Atualizar"** (ao lado dos atalhos de filtro): agora faz uma **sincronização sob demanda antes de re-buscar**. Ao clicar: 1) chama `POST /api/sync/atualizar` (`dispararSincronizacao()` em `lib/api.js`), que dispara o webhook do n8n configurado no backend (`N8N_SYNC_WEBHOOK_URL`) — esse webhook busca no Asaas, agrupa e já sincroniza nosso banco antes de responder; timeout de 35s no frontend (um pouco maior que os 30s do backend, pra deixar o backend responder primeiro com sua própria mensagem de timeout); 2) só depois dessa chamada retornar (sucesso **ou** falha) é que re-busca a página atual da tabela e os cards de resumo juntos (`Promise.all`), assim, se a sincronização deu certo, a re-busca já reflete os dados novos; 3) se o webhook falhar ou der timeout, a re-busca normal acontece do mesmo jeito (não trava o botão) e aparece um aviso curto ao lado ("Sincronização falhou, exibindo últimos dados", ícone `IconAlert`, com a mensagem de erro completa no tooltip) — a mensagem "Atualizado agora" só aparece quando a sincronização em si teve sucesso, não só porque a re-busca local rodou.
- **Modal de detalhe** (abre ao clicar na linha) — dados cadastrais (incluindo e-mail, quando o associado tiver um vindo do `POST /api/sync`, e, desde o **AJUSTE 9**, um campo **"Nome"** com o nome exatamente como cadastrado no Asaas — `nome_asaas`, verbatim, sem nenhum tratamento do Gestor, incluindo o prefixo numérico que o Asaas usa; mostra "-" enquanto o backfill/sync ainda não populou; o título do modal continua usando `nome`, sem relação com esse campo novo — ver README do backend, seção "AJUSTE 9"), badges de Bloqueado/Jurídico, cobranças em aberto com link de pagamento, seção **Controle de bloqueios** (contador do ciclo via `GET .../bloqueios/contador`, badge de risco de perda de cashback a partir de 4 bloqueios, botão de reset com confirmação via `POST .../bloqueios/resetar`), seção **Histórico** e campo de observação editável — logo abaixo do campo, mostra "Última observação: há Xd" (ou "hoje"/"há 1 dia") com a data completa entre parênteses, calculado a partir de `observacao_atualizada_em`, e o mesmo indicador amarelo de "sem contato recente" da tabela quando aplicável.
  - **Histórico** consome o campo único `historico` de `GET /api/associados/:cpf_cnpj` (ver README do backend — tabela `historico_status_associado`) e mostra, mais recente primeiro, toda mudança de "Negociação", "Bloqueio" **ou** "Jurídico" do associado — cada linha identifica qual dos três campos mudou, o valor anterior, o valor novo e a data/hora. Antes, essa seção só existia para negociação e nem sequer registrava mudanças de status jurídico.
- **`/inadimplencia`** — protegida, acessível pelo link "Taxa de Inadimplência %" no cabeçalho (entre Dashboard e Cadastro). Consome `GET /api/inadimplencia/resumo`, que calcula os números **em tempo real** a partir da API do Asaas (pode demorar alguns segundos — ver indicador de carregamento abaixo).
  - **Cards de resumo** (`components/ResumoInadimplenciaCards.js` — reorganizado no **AJUSTE 16**, ver seção própria mais abaixo para o desenho completo): 3 linhas, 8 cards. Linha 1, em destaque (mesmo peso visual, fonte grande) — **Total Faturado**, **Total em Aberto** (soma bruta de tudo ainda não pago, sem toggle) e **Total Recebido**. Linha 2, menores — **Taxa de Inadimplência** (cor muda com a gravidade: verde `<5%`, amarelo `5-15%`, laranja `15-30%`, vermelho `≥30%` — faixas de corte são decisão de design do frontend, o backend só manda o número), **Taxa de Adimplência** e **Associados Inadimplentes**. Linha 3, extra — **Renegociações Abertas** (quantidade + valor) e **Críticos 90+ dias**. Os cards Total Recebido/Taxa de Inadimplência/Taxa de Adimplência mostram um subtexto pequeno ("Situação atual" ou "Fechamento histórico do mês" — nomes novos, AJUSTE 15) indicando qual critério de cálculo está em uso — o mesmo toggle do bloco "Análise" da barra de filtros abaixo, que **desde o AJUSTE 6** também controla esses cards, não só o gráfico de faixas (ver README do backend); Total Faturado/Total em Aberto não seguem esse toggle.
  - **Filtros (AJUSTE 15 — Repaginar filtros da Taxa de Inadimplência, reorganização completa da barra)**: agrupados em 5 blocos visuais lado a lado (`components/BlocoFiltro`, definido em `app/inadimplencia/page.js`), em vez da lista corrida de antes — "Período", "Situação", "Análise", "Faixa" e "Tipo de inadimplente":
    - **Período**: "De"/"Até" (`components/DatePicker.js`, mesmo calendário usado em `/cadastro`) + um `<select>` novo **"Filtrar período por"** (Data de emissão | Data de vencimento — padrão | Data de pagamento/recebimento), que decide qual campo de data o período filtra (`filtro_periodo` — ver README do backend). Em "Data de pagamento/recebimento", cobranças ainda não pagas ficam de fora, mesmo dentro do período.
    - **Situação**: novo filtro **"Situação da cobrança"** (`components/MultiCheckboxFilter.js`, checkbox múltiplo — Todas/Em aberto/Pagas, combináveis), mapeado pro parâmetro `situacao` da API. Diferente do antigo "Tipo de pendência" (removido desta tela — ver nota abaixo), filtra a **população inteira**, não só o valor inadimplente.
    - **Análise**: o toggle que decidia "Em aberto hoje"/"Histórico do período" — antes no cabeçalho do gráfico de faixas — mudou de posição (agora fica neste bloco da barra de filtros) e de nome: **"Situação atual"** / **"Fechamento histórico do mês"** (mesmo parâmetro `visao` de sempre, sem mudança de comportamento, só de rótulo/posição).
    - **Faixa**: "Faixa de atraso" deixou de ser um `<select>` de escolha única e virou checkbox múltiplo (`MultiCheckboxFilter`) — Todas/Em dia/1-20/21-30/31-40/41-50/51-100/Acima de 100 (rótulos "Em dia"/"Acima de 100" só no filtro; o gráfico abaixo continua com "Até o vencimento"/"100d+" no eixo). Continua sendo aplicado **na hora**, sem nova chamada à API (só destaca/esmaece barras no gráfico) — clicar numa barra do gráfico também alterna a inclusão dela na seleção.
    - **Tipo de inadimplente**: `components/StatusAssociadoFilter.js` — o antigo tri-state exclusivo "Jurídico" (Todos/Só ativos/Só Jurídico) virou checkbox múltiplo **combinável**: Ativo/Recuperável, Jurídico, Crítico (90+ dias — associado com pelo menos 1 cobrança nessa faixa de atraso, respeitando o bloco "Análise" acima). Um associado Jurídico com dívida de 100+ dias aparece marcado em "Jurídico" **e** "Crítico" ao mesmo tempo, sem duplicar valor na soma (ver README do backend). Mapeado pro parâmetro `tipo_inadimplente` (a API ainda aceita o antigo `em_juridico`, só não é mais usado por esta tela). **Os checkboxes "Em negociação"/"Bloqueado" que ficavam aqui saíram da tela na correção pós-entrega deste ajuste** (ver seção "AJUSTE 15 (2ª correção pós-entrega)" mais abaixo) — o parâmetro do backend continua intacto, só a UI parou de oferecer essa opção.
    - Botões **Aplicar**/**Limpar** continuam abaixo dos blocos. "Período" e "Tipo de inadimplente" disparam uma nova chamada à API (por isso ficam "represados" até Aplicar); "Situação" também, por ser filtro de população; "Análise" e "Faixa" continuam aplicando **na hora** (sem novo request), exatamente como já era o toggle/dropdown antigos que substituem.
    - **Removido desta tela**: "Tipo de pendência" (Todas/Só vencidas/Só confirmadas — AJUSTE 4). O novo brief de filtros não previu um lugar pra ele nos 5 blocos, e "Situação da cobrança" cobre a distinção mais usada na prática (em aberto x pagas). O parâmetro `tipo_pendencia` continua existindo e funcionando no backend (compatibilidade) — só deixou de ser enviado por esta tela, o que equivale a sempre "todos" (o próprio padrão de antes).
  - **Gráfico de faixas** (`components/FaixasChart.js`): barras verticais com o valor em atraso (R$) de cada uma das 7 faixas (`ate_vencimento`, `1_20`, `21_30`, `31_40`, `41_50`, `51_100`, `acima_100` — ver AJUSTE 5 no README do backend; a faixa `acima_100` não tem teto superior). Cores em rampa de calor, **interpoladas entre as 4 cores semânticas de atraso já existentes no app** (verde → amarelo → laranja → vermelho — ver `lib/atraso.js`/seção de faixas de cor abaixo), então a paleta de marca continua com uma cor só e nenhuma cor nova é introduzida. Clicar numa barra (ou marcar no bloco "Faixa" da barra de filtros) alterna a inclusão dela na seleção, destacando as marcadas e esmaecendo as demais. **Desde o AJUSTE 15**, o toggle "Situação atual"/"Fechamento histórico do mês" saiu do cabeçalho deste gráfico e foi pro bloco "Análise" da barra de filtros (ver acima) — o componente só recebe `visao` já decidido, pra ajustar o texto de apoio abaixo do título. "Situação atual" é o padrão, sem nenhuma mudança de comportamento; "Fechamento histórico do mês" reclassifica as cobranças pela data de pagamento em vez do status atual. Desde o AJUSTE 6, esse mesmo `visao` também controla os cards Valor Inadimplente/Valor Adimplente/Taxa de Inadimplência do topo da tela (ver acima) — antes ele só afetava este gráfico.
  - **Top 10 devedores** (`components/TopDevedores.js`): lista com barra horizontal proporcional ao valor de cada devedor, nome + CPF/CNPJ, ordenados do maior para o menor — direto do array `top_devedores` da resposta.
  - **Exclusão de cobranças por palavra-chave** (`components/ExclusoesPanel.js`, seção "Palavras-chave excluídas" na tela) — mesmo campo único de sempre (lista de palavras, adicionar/remover, case-insensitive), mas **desde o AJUSTE 7** o critério de match deixou de olhar só a descrição da cobrança: agora também compara, palavra a palavra, contra o CPF/CNPJ do associado (com ou sem pontuação — funciona configurar tanto "12.345.678/0001-90" quanto "12345678000190") e contra o nome/razão social do associado. Nenhuma mudança visual na lista nem no fluxo de adicionar/remover — só o critério de match ficou mais abrangente (ver README do backend, seção "Exclusão de cobranças do cálculo").
- **Chave do Asaas não configurada**: se `GET /api/inadimplencia/resumo` responder `400` com uma mensagem citando `"asaas-key"` (é como o backend sinaliza esse caso — ver README do backend), a tela troca todo o conteúdo por um aviso claro com um botão "Ir para Configurações" (`Link` para `/configuracoes`), em vez de mostrar cards/gráficos vazios ou um erro genérico.
  - **Indicador de carregamento**: enquanto a chamada ao Asaas está em andamento, os cards mostram skeletons pulsantes (mesmo padrão do dashboard) e aparece um aviso de texto com spinner ("Consultando a API do Asaas — isso pode levar alguns segundos") logo abaixo dos filtros, já que essa chamada é sensivelmente mais lenta que as demais do app (depende de uma API externa, não só do nosso banco).
- **`/juridico`** — protegida, acessível pelo link "Jurídico" no cabeçalho (entre Taxa de Inadimplência % e Cadastro). Quadro Kanban por franquia (`app/juridico/page.js`):
  - **Etapas (colunas)**: criar (`+ Nova etapa`), renomear (clique no nome da coluna), reordenar (arrastar pelo cabeçalho da coluna) e excluir — se a etapa tiver algum card, mostra um modal de confirmação citando quantos cards serão removidos junto (`409` do backend com `total_cards`); confirmando, chama de novo com `?confirmar=true`.
  - **Cards — duas origens**: "Vincular associado" (busca por nome/CPF-CNPJ/telefone com debounce de ~350ms, `GET /api/juridico/associados-busca`, mesmo padrão de busca do Dashboard) — o card mostra nome, CPF/CNPJ, telefone e valor em aberto **sempre em tempo real** (vêm do board a cada `GET /api/juridico/etapas`, nunca de um valor salvo no card); ou "Livre" — título + descrição + **observações** próprios. Nos dois casos, "Responsável" e "Prazo" são campos opcionais. **Atualização:** Descrição/Observações deixaram de ser exclusivos de card "Livre" — o modal (`ModalCard`) mostra os dois textareas **sempre**, nos dois modos; só o campo Título continua exclusivo de "Livre" (num card vinculado, o título segue sempre o nome do associado, sem campo próprio pra editar). No card do board, observações aparecem em itálico quando presentes, também nos dois modos.
  - **Drag and drop nativo** (API HTML5 `draggable`/`onDragStart`/`onDrop`, sem biblioteca externa — o projeto não usa nenhuma): arrastar um card entre colunas ou dentro da mesma coluna chama `PATCH /api/juridico/cards/:id/mover`; arrastar o cabeçalho de uma coluna pra outra posição chama `POST /api/juridico/etapas/reordenar`. Nenhuma atualização otimista — cada ação recarrega o board inteiro depois de confirmada pela API (mesmo padrão simples já usado em Controle Geral).
  - **Editar/excluir card**: botões inline em cada card, abrem o mesmo modal de criação (pré-preenchido) ou removem direto (`DELETE /api/juridico/cards/:id`). **Aba "Histórico"**: editando um card já existente (não aparece na criação de um card novo, que ainda não tem histórico), o `ModalCard` ganha um seletor "Dados"/"Histórico" no topo — "Histórico" chama `GET /api/juridico/cards/:id/historico` (`lib/api.js:historicoCardJuridico`) e lista cada evento (campo alterado com rótulo amigável via `CAMPO_HISTORICO_LABEL`, valor anterior → valor novo, quem fez a mudança ou "Sistema (API)" quando não há usuário associado, e quando, formatado por `formatDateTime`), mais recente primeiro.
  - **AJUSTE 10 — destacar card via `?card=<id>`**: chegar aqui pelo link "Ver no Jurídico" do aviso do Dashboard (ver acima) traz um `?card=<id>` na URL — depois que o board carrega, a página rola até esse card e aplica um anel laranja por 4s, pra localizá-lo sem precisar procurar coluna por coluna; a URL é limpa de volta pra `/juridico` logo em seguida (`router.replace`, `next/navigation`). Se o card não existir mais (excluído entre o aviso e o clique), desiste silenciosamente. Como `useSearchParams` exige um limite de Suspense acima dele no App Router, o board de verdade mora num componente interno (`JuridicoBoard`); o `export default` só adiciona esse limite.
  - **AJUSTE 11 — aba "Documentos"**: editando um card **vinculado a associado** (não aparece pra card "Livre" nem na criação de um card novo), o `ModalCard` ganha uma 3ª aba, "Documentos", ao lado de "Dados"/"Histórico". Lista os documentos anexados ao associado daquele card (`GET /api/juridico/associados/:cpf_cnpj/documentos`), com upload (`<input type="file">` restrito a PDF/DOCX/XLSX/JPG/PNG + descrição opcional), "Baixar" (busca o arquivo autenticado como blob e dispara o "salvar como" do navegador) e "Excluir" (com confirmação) por documento — ver componente `DocumentosCard`, novo em `app/juridico/page.js`.
- **`/cadastro`** — protegida, acessível pelo link "Cadastro" no cabeçalho. Formulário de Cadastro/Faturamento que substitui o gatilho do Kommo, organizado em 4 seções:
  - **Identificação**: Tipo de Pessoa (toggle PF/PJ), Razão Social, Nome Fantasia, CNPJ/CPF (máscara dinâmica conforme o tipo selecionado — `000.000.000-00` para PF, `00.000.000/0000-00` para PJ).
  - **Endereço**: CEP (máscara `00000-000`), Endereço, Número, Complemento (opcional), Bairro, Cidade, UF (dropdown com as 27 siglas de estado).
  - **Contato**: Contato, Celular (máscara `(00) 00000-0000`/`(00) 0000-0000` conforme a quantidade de dígitos), E-mail (validado por formato antes do envio).
  - **Faturamento**: Descrição do Serviço (dropdown travado nas 4 opções exatas exigidas pelo backend), **Nome da pasta** (opcional, texto livre — nome da pasta do associado a ser criada no Google Drive), **Créditos VP$** (opcional, dropdown Nenhum/2.000/8.000), **Contratos a gerar** (opcional, checkboxes com os modelos de contrato **ativos** carregados de `GET /api/contratos?ativo=true`), Valor da Entrada (opcional, campo monetário R$), **Data da Entrada** (opcional, calendário — mesmo componente de "Data Vencimento" — relevante quando há "Valor da Entrada" > 0; se ficar vazio, o backend assume a data de envio do cadastro como fallback), Número de Parcelas (dropdown 1x–12x), Valor Total, Data Vencimento (calendário customizado com navegação por mês, `components/DatePicker.js`), Observações (textarea) e Desconto Parcela (opcional, campo monetário).

  **"Créditos VP$" é um campo novo, sem pedido explícito** — adicionado porque a função `creditosVps()` do backend (usada na geração automática de contratos) só aceita os valores 8000/2000/0, e nenhum campo existente do formulário mapeava pra isso; ver "Premissas assumidas" no README do backend.

  Os campos monetários (`Valor da Entrada`, `Valor Total`, `Desconto Parcela`) usam uma máscara "de digitação": o estado guarda o valor em centavos e a exibição é formatada como moeda BRL a cada tecla (`lib/mascaras.js`); no envio, são convertidos para string decimal (`"1500.00"`), igual ao formato usado nos testes do backend.

  Depois de `POST /api/cadastros` responder, quem decide o que mostrar é o campo `status` do corpo, não o status HTTP (que é sempre `201` — ver README do backend): `status: "enviado"` mostra a mensagem de sucesso e, se `link_pagamento` vier preenchido, um link clicável pro pagamento gerado pelo n8n (Asaas); `status: "erro"` mostra o motivo real vindo de `resposta_n8n` (timeout, CPF inválido, cliente já existe no Bling etc.) em vez de assumir sucesso — o formulário só é limpo quando `status` é `"enviado"`. `criarCadastro` usa um timeout de 65s no fetch (o backend espera até 60s pelo n8n, que encadeia Bling + Asaas com retries).

  Validação client-side antes do `POST /api/cadastros`, espelhando exatamente as regras do backend: `CNPJ/CPF` obrigatório, `Razão Social` **ou** `Contato` obrigatório, `Descrição do Serviço` obrigatório, `Valor Total` obrigatório, e `E-mail` (quando preenchido) precisa ter formato válido — erros aparecem num banner listando cada mensagem, sem chegar a enviar a requisição. O payload é montado com as chaves **exatamente** como o backend espera (em português, com acento/espaço: `"Tipo de Pessoa"`, `"Razão Social"`, `"CNPJ/CPF"`, `"Descrição do Serviço"` etc. — ver `criarCadastro` em `lib/api.js`). Após um envio bem-sucedido, um banner verde de confirmação aparece e o formulário inteiro é limpo para o próximo cadastro; erros de rede/API (ex.: 400 de validação vindo do backend) aparecem no `ErrorBanner` padrão do app.
- **`/contratos`** — protegida, acessível pelo link "Contratos" no cabeçalho (entre Cadastro e Configurações). CRUD dos modelos usados na geração automática de contratos:
  - **Lista**: nome, badge de tipo (Termo de Associação/Aditivo Contratual) e badge Ativo/Inativo, ordenados mais recentes primeiro (`GET /api/contratos`, sem filtro — traz ativos e inativos).
  - **Novo modelo / Editar**: formulário inline com Nome (texto), Tipo (select) e Conteúdo — um editor de texto rico (`components/RichTextEditor.js`, [Tiptap](https://tiptap.dev/)) com negrito, itálico, sublinhado, títulos (H1/H2/H3), lista numerada, lista com marcadores e alinhamento de texto (esquerda/centro/direita/justificado), exportando/importando HTML puro (`<strong>`/`<em>`/`<u>`/`<h1-3>`/`<ol>`/`<ul>`/`<li>`/`style="text-align: ..."`). Itálico, sublinhado e lista com marcadores já vêm inclusos no `StarterKit` (não precisaram de extensão separada); alinhamento usa `@tiptap/extension-text-align`. Um banner amarelo avisa que as variáveis devem ser digitadas como texto simples no formato `{{Nome Da Variável}}` **sem formatação parcial** (ex.: não deixar só `{{Razão` em negrito) — a substituição no backend procura a chave inteira dentro da tag HTML e não encontra se ela for cortada por uma tag de formatação no meio.
  - **Desativar/Reativar**: soft-delete only (`PATCH { ativo: false }`/`{ ativo: true }` via `DELETE`/`PATCH /api/contratos/:id`) — nunca remove de verdade, pra não quebrar cadastros antigos que referenciam esse modelo (`modelosContratoIds`). Desativar tem confirmação em duas etapas, mesmo padrão de "Revogar" em Chaves de API.
- **`/configuracoes`** — também protegida, acessível pelo link "Configurações" no cabeçalho. Mostra a API key mascarada (`GET /api/config/api-key`), botão para regenerá-la com confirmação (`POST /api/config/api-key/regenerar`) que revela a chave completa uma única vez num modal com botão de copiar e aviso para atualizar integrações (ex.: n8n), uma seção para a **chave de API do Asaas** (campo mascarado + input + botão "Salvar", mesmo padrão visual da chave interna — mas sem o fluxo de regeneração aleatória, já que essa chave é colada manualmente pelo usuário, vinda do painel do Asaas; usa `GET`/`PATCH /api/config/asaas-key`, com link direto para a tela `/inadimplencia`), um card **"Pasta raiz do Google Drive"** (input + botão "Salvar", aceita ID puro ou link completo da pasta — `GET`/`PATCH /api/config/drive-pasta-raiz` — usada pela geração automática de contratos pra saber onde criar a pasta de cada associado), e uma tabela com o log das últimas 20 sincronizações (`GET /api/config/sync-log`).
- **`/controle-geral`** — multi-franquia, Etapa 5 (ver README do backend, "Testes realizados" → "Multi-franquia — Etapa 5"). Protegida em duas camadas: `RequireAuth` (sessão válida) e `components/RequireSuperAdmin.js` (redireciona pro Dashboard quem não é `SUPER_ADMIN` — só UX; a proteção real é o backend, `middleware/exigirSuperAdmin.js`, `403` em toda rota). O link "Controle Geral" no cabeçalho só aparece pra quem tem `papel: "SUPER_ADMIN"` no claim do próprio access token (`lib/auth.js:isSuperAdmin()`, decodifica o JWT no navegador sem verificar assinatura — só UX, não segurança). Duas seções:
  - **Franquias**: lista com nome, status (Ativa/Inativa) e data de criação, cada uma já com o usuário titular embutido (`GET /api/franquias`). "Nova franquia" abre um formulário que pede nome da franquia **e** os dados do usuário titular juntos (nome, e-mail, senha) — não existe fluxo de criar franquia sem usuário (`POST /api/franquias`). Nome editável inline a qualquer momento (`PATCH /api/franquias/:id`). "Desativar franquia"/"Reativar franquia" com confirmação em duas etapas (mesmo padrão de "Revogar" em Chaves de API) — bloqueia/libera o login do usuário titular imediatamente, **reversível**. Ao lado desse botão (não no lugar dele), um novo botão **"Excluir franquia"** — ALTO RISCO, `DELETE /api/franquias/:id/excluir-permanente` (`lib/api.js:excluirFranquiaPermanentemente`) — abre `ModalExcluirFranquia`: confirmação em duas etapas exigindo digitar o nome **exato** da franquia (mesmo padrão do GitHub pra apagar um repositório), com aviso explícito de que a ação é **irreversível** e apaga todos os dados da franquia dentro do Gestor, mais o mesmo aviso do backend de que contas externas (Asaas, Bling, Google Drive) **não** são apagadas.
  - **Usuários** (dentro do card de cada franquia, não numa tela separada — uma franquia deixou de estar limitada a 1 usuário, ver "Múltiplos usuários por franquia" no README do backend): lista de todos os usuários da franquia (mais antigo primeiro — o titular sempre aparece antes dos extras), cada um com nome, e-mail, badge Ativo/Bloqueado, botão "Bloquear"/"Desbloquear" (`PATCH /api/usuarios/:id`, confirmação em duas etapas), "Resetar senha" (`POST /api/usuarios/:id/resetar-senha`, campo inline pra nova senha, mín. 8 caracteres) e o próprio bloco de "Telas liberadas" (editável individualmente — ver abaixo). Botão **"+ Adicionar usuário"** por franquia abre um formulário inline (nome/e-mail/senha/checkboxes de recursos) que chama `POST /api/franquias/:id/usuarios` — todos os usuários da mesma franquia compartilham os mesmos dados/integrações, só as telas liberadas variam por login. Franquias que nunca passaram por "Nova franquia" nem "+ Adicionar usuário" (hoje, na prática, só a franquia padrão semeada pela migração da Fase 1) mostram "Nenhum usuário vinculado a esta franquia" em vez de quebrar.
  - **Meu perfil**: card separado pro próprio SUPER_ADMIN trocar nome, e-mail e/ou senha (`GET`/`PATCH /api/perfil`) — sempre exige a senha atual, mesmo pra trocar só o nome.
  - **Seletor de franquia** (`components/FranquiaSelector.js`, dropdown no cabeçalho, só visível pra `SUPER_ADMIN`): escolhe/troca a franquia "ativa" — persistida em `localStorage` (`lib/auth.js:setFranquiaSelecionada`), anexada como `?franquia_id=...` em toda chamada autenticada (`lib/api.js:comFranquiaSelecionada`). Trocar de franquia faz uma navegação **dura** (`window.location.href`, não `router.push`) de propósito — força toda página/componente já montado a remontar do zero com os dados da franquia nova, mais simples e robusto do que sincronizar estado entre componentes independentes (única exceção de navegação client-side documentada no projeto — precisou de `eslint-disable-next-line` explicado no código pra 2 regras do lint que assumem o padrão contrário). Sem uma franquia selecionada, Dashboard/Cadastro/Contratos/Configurações/Taxa de Inadimplência/Jurídico mostram um estado vazio orientando a escolher (`components/RequireFranquiaSelecionada.js`) em vez de tentar renderizar dados — "Controle Geral" é a única tela que não passa por esse guard, por ser cross-franquia por natureza.
  - **Telas liberadas por franquia** (restrição de recursos, ver README do backend): cada franquia, dentro do card dela, mostra as telas liberadas como badges ("Telas liberadas: Dashboard, Jurídico...") com um link "editar" que troca pra um grid de checkboxes (`lib/recursos.js`, mesmas 6 chaves usadas no backend) — salvar chama `PATCH /api/franquias/:id` com `recursos_permitidos`. No formulário "Nova franquia", os mesmos checkboxes aparecem todos marcados por padrão (mais fácil desmarcar o que não quer do que esquecer de marcar o que precisa), ajustáveis antes de criar.

### Restrição de telas por franquia (frontend)

Além do que o SUPER_ADMIN configura em Controle Geral (acima), cada usuário de franquia só vê e acessa as telas liberadas pra ele — em duas camadas, as duas só de UX (a proteção real é sempre o backend, `middleware/exigirRecurso.js`, `403` em toda rota mesmo se o frontend for contornado):

- **Menu** (`components/AppHeader.js`): cada link de `NAV_LINKS` tem uma chave `recurso` (`dashboard`/`inadimplencia`/`cadastro`/`contratos`/`juridico`/`configuracoes`); só aparece se `temRecurso(recurso)` (`lib/auth.js`) for `true` pra sessão atual. `SUPER_ADMIN` sempre vê todos os links, mais "Controle Geral" (nunca restringível).
- **Acesso direto pela URL** (`components/RequireRecurso.js`, usado em cada um dos 6 `layout.js` restringíveis): se a franquia não tiver o recurso daquela tela, mostra um estado "Sem acesso a esta tela" em vez do conteúdo — não quebra a aplicação, não redireciona (diferente de `RequireSuperAdmin.js`, que redireciona pro Dashboard).
- **`temRecurso`/`isSuperAdmin`** decodificam o claim `recursosPermitidos` do access token (mesmo padrão de `getClaims()` já usado pra `papel`/`franquiaId` — decodifica sem verificar assinatura, só UX) — pode ficar desatualizado até o token expirar (15min por padrão) se o SUPER_ADMIN mudar os recursos no meio da sessão; se isso acontecer, a tela ainda renderiza (claim stale), mas as chamadas de API tomam `403` normalmente e mostram o erro de sempre — não quebra, só não antecipa o bloqueio no clique do menu.

### Faixas de cor por atraso (cores fixas, fora da paleta do tema)

Calculadas a partir da cobrança em aberto (`pending`/`overdue`) mais atrasada de cada associado. **Convenção do `dias_diferenca` (vem do backend): negativo = dias em atraso; zero ou positivo = dias até o vencimento** (ou já vencendo hoje, no caso do zero).

| Faixa | Cor | Critério |
|---|---|---|
| Em dia | Verde | sem cobrança em aberto, ou `dias_diferenca >= 0` |
| Atenção | Amarelo | `dias_diferenca` entre -1 e -9 |
| Alerta | Laranja | `dias_diferenca` entre -10 e -19 |
| Crítico | Vermelho | `dias_diferenca <= -20` |

> Havia um bug nessa lógica em uma versão anterior, com o sinal invertido (tratando positivo como atraso). Foi corrigido em `lib/atraso.js` — a função que encontra a cobrança mais crítica também passou a usar o menor valor de `dias_diferenca` (mais negativo), não mais o maior.
>
> As faixas numéricas também já mudaram uma vez desde então: os limites originais (amarelo até -15, laranja até -30, vermelho a partir de -31) foram substituídos pelos atuais (amarelo até -9, laranja até -19, vermelho a partir de -20) — ver "Testes realizados" para a validação das fronteiras.

## Deploy no Vercel

1. Importe o repositório (ou a pasta `frontend`, se for um monorepo) no [Vercel](https://vercel.com/new).
2. Framework Preset: **Next.js** (detectado automaticamente).
3. Em *Environment Variables*, defina:
   - `NEXT_PUBLIC_API_URL` → URL pública da API backend em produção.
4. Deploy. Builds seguintes acontecem automaticamente a cada push.

> Como a API já roda em outro servidor, garanta que ela aceite requisições vindas do domínio do Vercel (CORS liberado) — o backend deste projeto já habilita CORS por padrão.

### Sessão do login: access token curto + refresh token (correção de bug)

**Bug relatado**: "sessão expira, peço login de novo, mas o token continua sendo o mesmo depois de logar de novo." Investigado a fundo antes de qualquer fix — a causa raiz estava no **backend**, não no frontend: `jwt.sign` (a lib usada pra assinar o JWT) é determinístico, e o login antigo assinava só `{ sub: usuario }` com um token de vida longa (8h) sem nenhum campo único por sessão — dois logins com as mesmas credenciais dentro do mesmo segundo geravam o token **idêntico**, byte a byte. Ver "Autenticação do painel: access token curto + refresh token" no README do backend pro diagnóstico completo (incluindo a reprodução empírica) e o fix aplicado lá.

**O que muda no frontend** (`lib/auth.js`, `lib/api.js`):

- `login()` agora retorna `{ token, refresh_token }` (antes só `token`) — `setSession({ token, refreshToken })`, nova função em `lib/auth.js`, guarda os dois no `localStorage` (`gdi_token` e `gdi_refresh_token`). `setToken`/`clearToken` continuam existindo (`clearToken` agora limpa os dois).
- `isAuthenticated()` passou a checar a presença do **refresh token**, não do access token — o access token agora vence sozinho a cada poucos minutos por design (`JWT_EXPIRES_IN=15m` no backend), isso é esperado e não significa "sessão encerrada". Antes, `isAuthenticated()` só checava presença (não validade) do único token que existia — checar o refresh token em vez do access token é o sinal certo de "existe uma sessão", já que ele é quem sustenta a sessão de verdade agora.
- `request()` (o helper central de chamadas à API) ganhou **renovação silenciosa**: um 401 numa chamada autenticada agora dispara `POST /api/refresh` com o refresh token guardado, e a chamada original é refeita automaticamente uma vez com o access token novo — o usuário nunca vê o erro nem precisa digitar a senha de novo, a não ser que o refresh token em si esteja ausente/expirado/revogado (aí sim `clearToken()` roda e a chamada falha, levando o `RequireAuth` a mandar pro `/login` na próxima navegação).
- **Guarda contra corrida**: se várias chamadas autenticadas levarem 401 ao mesmo tempo (comum — várias seções de uma tela buscando dados em paralelo), só a primeira dispara `POST /api/refresh`; as demais esperam essa mesma promise em vez de cada uma tentar renovar por conta própria. Isso importa porque o backend **rotaciona** o refresh token a cada uso (um valor só serve uma vez) — sem essa trava, duas renovações concorrentes se invalidariam uma à outra.
- `AppHeader`'s "Sair" agora chama `POST /api/logout` (revoga a sessão no servidor — ninguém mais renova ela) antes de limpar o `localStorage` e redirecionar; best-effort (não bloqueia o clique esperando a rede).

`RequireAuth.js` e `app/login/page.js` não precisaram mudar — os dois já usavam `isAuthenticated()` de `lib/auth.js`, e o comportamento correto (checar o refresh token) veio de graça ao trocar a implementação dessa função.

- `npm run lint` e `npm run build` (cópia fresh em `/tmp`) — limpos, 0 erros/warnings, as 8 rotas continuam prerenderizando normalmente.
- Validado de ponta a ponta contra um servidor real (não mock) — ver `test-auth-refresh.js` no README do backend, 22/22, incluindo a reprodução do bug original (dois logins simultâneos com as mesmas credenciais geravam o mesmo token antes do fix; depois, sempre diferentes) e o fluxo completo de expiração → renovação silenciosa → revogação.

**2. `components/FaixasChart.js` — bug de alinhamento na última coluna ("Acima de 100")**: a linha de barras usava flexbox (`flex` + `flex-1` em cada botão de faixa). Causa raiz: item de flexbox tem `min-width: auto` por padrão — o navegador nunca encolhe um item abaixo da largura mínima do próprio conteúdo, mesmo com `flex-1`. "Acima de 100" é o rótulo mais comprido das 7 faixas; num card estreito (o gráfico divide a linha com "Principais devedores" em `lg:grid-cols-2`), a largura mínima desse texto podia superar a fatia "justa" que sobraria pra ele, empurrando esse botão (rótulo + barra) pra fora do alinhamento das outras 6 colunas — exatamente o sintoma do print (rótulo solto em cima à direita, barra como uma linha fina fora da grade).

Corrigido trocando a linha de `flex`/`flex-1` por **CSS Grid** (`grid`, `gridTemplateColumns: "repeat(7, minmax(0, 1fr))"`): o `minmax(0, 1fr)` zera explicitamente o mínimo automático de cada coluna (o mesmo papel que `min-w-0` teria em flexbox) — as 7 colunas ficam **sempre** do mesmo tamanho, texto e barra presos à mesma grade, não importa o comprimento do rótulo ou o valor de cada faixa. `min-w-0` também adicionado ao botão de cada faixa (defensivo) e `break-words text-center` nos rótulos (valor/%/nome da faixa), pra que um texto longo quebre linha dentro da própria coluna em vez de forçar a coluna a crescer. Skeleton de loading (linha de barras cinza-pulsante) recebeu o mesmo tratamento, pra não divergir visualmente do estado carregado. Nenhuma mudança de cálculo (`alturaPx`/`ALTURA_MAXIMA_PX`/`ALTURA_MINIMA_PX` intactos) — só o container de layout.
